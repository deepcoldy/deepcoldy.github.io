      #Architecture overview

      What botmux does fits in one sentence: it turns Lark messages into input for an AI coding CLI, and turns the CLI's output back into Lark cards. This page covers which processes make up botmux, how a message flows through them, and what happens on restart. You don't need any of this for day-to-day use; come back when you're troubleshooting or contributing.

      #The big picture

      #What each process does

      ProcessHow manyWhat it does
      supervisor1 per machineThis is what botmux start launches. It starts each bot's daemon, the Dashboard and plugin services, and restarts any of them that crash
      daemon1 per botHolds the Lark long connection, decides whether a message should be handled and which session it belongs to, handles slash commands, and creates, restores and closes sessions
      worker1 per active topicLaunches the CLI through an adapter, types Lark messages into it, and turns terminal output into streaming cards; also serves the session's web terminal
      CLI process1 per topicThe AI coding CLI doing the actual work, running inside tmux or another backend, exactly as if you used it in your own terminal
      dashboard1 per machineThe admin dashboard, port 7891 by default

      Key points:

      • One daemon per bot, fully isolated. A problem in one bot won't take the others down. See Multi-bot.
      • A "session backend" sits between the worker and the CLI. The default is tmux: the CLI lives inside tmux, so restarting the worker or daemon doesn't interrupt it.
      • Want to drive a CLI over HTTP without Lark at all? Use the single-process Core-only mode. It skips the supervisor and doesn't need bots.json.

      #How a message flows

      Take "@ the bot in a topic and say something" as an example:

      1. Lark pushes the message to the daemon. The daemon first decides whether to handle it: was the bot @-mentioned, is this a topic it owns, does the sender have permission.
      2. Slash commands are recognized. Messages starting with / are classified against the command table (e.g. /close, /restart) and either handled by the daemon or passed to the CLI. Full list in Slash commands.
      3. The session is found or created. A new topic starts a new worker and CLI; an existing session is reused and the message is typed into the running CLI.
      4. Output becomes cards. The worker keeps reading the CLI's output, converts it to Markdown, updates the streaming card in Lark in real time, and posts the final reply when the turn ends.
      5. The CLI can also send messages on its own. botmux injects a set of built-in Skills into the CLI (such as botmux-send, botmux-schedule, botmux-history), which it uses to post to the topic, create scheduled tasks, read chat history and more. See Skills and CLI commands.

      #What happens on restart

      botmux restart restarts the daemon and workers. Whether the CLI restarts too depends on the session backend:

      BackendHow to enableAfter a daemon restart
      tmux (default)Nothing to configureThe CLI keeps running; the next message reattaches automatically and context is kept
      zmx / zellij / herdrSet explicitly via backendType or BACKEND_TYPEAlso persistent; requires the matching tool
      ptySet explicitly via BACKEND_TYPE=pty or backendType: "pty"The CLI exits with the worker and is relaunched after restart

      If tmux isn't available, botmux does not silently fall back to pty. It blocks new sessions and shows a card asking you to install tmux. Details in Persistent tmux sessions and ZMX backend.

      On startup the daemon automatically restores previously active sessions, so you can keep chatting in your Lark topics after a restart.

      #Where files live

      PathContents
      ~/.botmux/bots.jsonBot configuration, see bots.json
      ~/.botmux/.envGlobal environment variables, see Environment variables
      ~/.botmux/data/Session data, one SQLite database per bot (session-stores/<appId>/sessions.db)
      ~/.botmux/logs/Logs: daemon-<index>-out.log / -err.log, dashboard-out.log and so on; or just run botmux logs

      #Source map (for contributors)

      If you want to change the code, start here:

      LocationResponsibility
      src/cli.ts, src/cli/The botmux command-line entry and its subcommands
      src/index-supervisor.ts, src/core/fleet-supervisor.tsSupervisor: starts and watches daemons, the dashboard and plugin services
      src/daemon.tsDaemon orchestration layer that wires the modules together
      src/worker.tsWorker process: manages the CLI, renders cards, serves the web terminal
      src/bot-registry.ts, src/config.tsLoading bots.json and global config
      src/adapters/cli/CLI adapters, one file per CLI (launch args, input method, Skill directory, etc.)
      src/adapters/backend/Session backends: tmux, pty, zmx, zellij, herdr and more
      src/core/Session management, command table and routing (command-schema.ts / command-router.ts), worker pool, scheduler, etc.
      src/im/lark/Lark: event dispatch, card building and callbacks, API calls, message parsing
      src/skills/Built-in Skills injected into the CLI
      src/dashboard/Admin dashboard
      src/utils/Idle detection, terminal screenshot rendering, logging and other utilities

      For the full steps to add a new CLI, see src/adapters/cli/CLAUDE.md in the repository.
